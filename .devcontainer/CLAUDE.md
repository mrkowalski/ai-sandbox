# .devcontainer — how the security contract is enforced

Loaded automatically when working with files under `.devcontainer/`.
Repo-wide context lives in the root `CLAUDE.md`.

Five files form one chain; a change to any of them is a change to the sandbox's guarantees. A sixth pair — the host-only command list and its guard — is layered on top; it is an ergonomics mechanism, not part of the security contract. Nothing it declares depends on it: each entry is held by the firewall, by absent credentials, or by the read-only `.git` mount described in 1.

1. **`devcontainer.json`** grants `NET_ADMIN`/`NET_RAW` (needed to install the firewall), makes the rootfs `--read-only` with a `/tmp` tmpfs, bind-mounts the host project at its own host path, binds that project's `.git` directory back over itself **read-only**, pins `"overrideCommand": false` so the CLI cannot discard the image `ENTRYPOINT` (see 2 — this one line is load-bearing and does not look it), and keeps bash history, Claude Code config, and npm's cache in per-project named volumes called `claude-code-<kind>-${localEnv:SBX_SLUG}-${devcontainerId}` — the workspace path, slugified by `sbx_slug` in the repo's `sbx-env.sh` and exported by whichever launcher was used, ahead of the id the CLI derives from the workspace folder. The two halves do different jobs, and the distinction is the whole point of the naming. The id is the uniqueness key: no launcher can fail to supply it, so two projects never share a volume. The slug is the label that makes `docker volume ls` legible, and it *can* be forgotten — a launch without `SBX_SLUG` names these volumes `claude-code-config--<id>`, still this project's alone but a second, stray set the wrappers will not mount again. An earlier revision of this file dropped `${devcontainerId}` and left the slug as the only key; a host run on 2026-09-23 established that an unscoped launch is *not* refused, which under that scheme would have pooled every project's Claude Code credentials and session history into one volume while the container looked entirely normal, and the id was put back. That is what `verify.sh`'s check 7 asserts: the mounted volume names against a slug re-derived inside the container from `SBX_WORKSPACE` (`${localWorkspaceFolder}`, passed through `containerEnv`), FAILing on a mismatch — re-derived rather than trusting `SBX_SLUG`, which would only prove the value equals itself, and requiring a non-empty id after the slug, which the container cannot recompute and so only requires be present. The npm cache volume at `/home/node/.npm` is what makes `npm install` and `npx` work at all: without it npm's cache lands on the read-only rootfs and every registry fetch dies with `EROFS`. It has to be a volume rather than a tmpfs because `npx` executes binaries it stages inside the cache, and the `/tmp` tmpfs is `noexec`. Its `postStartCommand` runs `init-firewall.sh && verify.sh` with `waitFor: postStartCommand`. **This is not what enforces the sandbox, and reading it that way is what let the firewall go missing unnoticed.** `waitFor` makes a failing verification fail the launch *command*; the container is already running by then and keeps running, and `devcontainer exec` is a separate invocation that will happily attach to it. It also does not run at all on `docker start`, a Desktop restart, or a restart after a host reboot — and iptables state does not survive a stop/start, so those come back with an empty ruleset. Enforcement lives in the entrypoint (2); `postStartCommand` is the full, network-probing verification pass and a redundant second install. Keep both as they are, but do not mistake either for the guarantee. The nested `.git` bind is the only thing that stops the agent writing the user's history, and it is a containment control rather than a convention: it is in force before any process in the container starts, it does not care whether a command came through the Bash tool or from inside a script, and the host-only guard's bypass does not touch it. It has to be expressed here because the container has `NET_ADMIN`/`NET_RAW` and *not* `CAP_SYS_ADMIN` — nothing inside the container can call `mount`, so an entrypoint remount was never an option, and granting `CAP_SYS_ADMIN` to gain one would trade a large class of escapes for a git guarantee. The cost is that `git add`, `git stash`, and `git checkout -b` stop working too; that is intended, since staging is writing the repository. Reads are untouched — measured, not assumed: `status`, `diff`, `log`, `show`, `branch`, `tag -l` all exit 0 with no warning. `initializeCommand` pre-creates the mount source on the host so that a workspace with no repository gets a user-owned empty `.git` instead of the root-owned one Docker would otherwise leave behind. Repos outside the workspace are unaffected, which `verify.sh`'s own scratch repo under `mktemp -d` depends on.

2. **`entrypoint.sh`** is the enforcement point, and the reason it is an image `ENTRYPOINT` rather than a devcontainer hook is that an `ENTRYPOINT` is part of the image: it runs on *every* start, however the container was started — **but only if the launch configuration lets it**, which is a condition, not a property. The devcontainer CLI defaults `overrideCommand` to true and creates the container with `--entrypoint /bin/sh`, discarding the image `ENTRYPOINT` entirely; on 2026-08-31 that left a container running wide open while the entrypoint sat installed and unused. `devcontainer.json` pins `"overrideCommand": false` and the Dockerfile supplies the keep-alive `CMD` that the CLI then stops providing. Those two lines and this one are a set: remove any of them and the enforcement point silently detaches. It installs the firewall, gates on `verify.sh --iptables-only`, writes the `/tmp/.sandbox-firewall-installed` marker, and only then `exec`s the container's command. **It fails closed by never reaching that `exec`** — a container whose firewall did not install stops instead of running, so there is nothing left for a session to attach to. The gate is deliberately the offline `--iptables-only` pass and not the full `verify.sh`: reachability is a health signal, not a containment property, and an Anthropic outage must report `NOT VERIFIED` rather than brick the sandbox. It runs as `node` and reaches root only through the two existing NOPASSWD sudoers entries, so it grants no new privilege.

3. **`allowed-domains.txt`** is the whole egress policy, one hostname per line, installed to `/usr/local/etc/`. Widening the sandbox means adding a line here — not adding an iptables rule. A name that fails to resolve aborts firewall setup by design.

4. **`init-firewall.sh`** captures the engine's container-DNS NAT rules (grepping `iptables-save -t nat` for Docker's `127.0.0.11`), sets all three chain policies to DROP, flushes, restores only those DNS rules, allows loopback and DNS, resolves each whitelisted host into the `allowed-domains` ipset, and finishes with a single ACCEPT for the ipset and a catch-all REJECT. **The DROP-before-flush order is the fail-closed guarantee**: there is no instant at which the chains are both emptied and permissive. It is reinforced by a `seal` EXIT trap with a `FIREWALL_OK` flag, so any abort — an unresolvable name, a DNS blip, an unreadable or empty whitelist, an undetectable host IP — ends with all three policies DROP and loopback only. Aborting on an unresolvable whitelist entry is still the contract; only the state it leaves behind changed, from open to sealed. The trap is `EXIT` rather than `ERR` because `ERR` is not inherited into every construct and would miss some exits.

5. **`verify.sh`** independently asserts the end state rather than trusting step 4: arbitrary egress is dead (`example.com` by name *and* by IP, HTTP and HTTPS), `git push --dry-run` fails over both SSH and HTTPS, `api.anthropic.com` is reachable, and the OUTPUT chain is genuinely in whitelist mode with a populated ipset. It also asserts that the three named volumes mounted into this container are the ones named for *this* workspace, reading their names out of `/proc/self/mountinfo` — the container has no Docker socket, so the mount table is the only place it can learn what it is mounted from. It asserts both halves of the writable-mount bargain: that npm's cache is writable *and* exec-capable, and that the rootfs outside the sanctioned mounts — `/usr/local/bin/`, the whitelist file, the global `node_modules` holding the `claude` binary, and `$HOME` itself — is still read-only. It asserts that the workspace's resolved git directory refuses a write while the repository still reads. The credential assertions that sit with the `git push` probes are FAILs, not WARNs, and detect key material by content of the directory rather than by an `id_*` glob — "no key in here" is a guarantee the sandbox makes, so a `deploy_key` or a stray `.pem` has to stop the launch like any other. And it asserts the enforcement point itself: that the entrypoint marker is present, meaning the firewall was installed at *this* start rather than by some earlier `devcontainer up`.

6. **`host-only-commands.txt`** and **`host-only-guard.sh`** are the sandbox's declaration of what it will not do. The list — one `<ERE>  ::  <what to tell the user>` entry per line, installed to `/usr/local/etc/` — is the only place a command is declared host-only; the guard holds no rules of its own. The guard runs as a `PreToolUse` hook on `Bash`, wired by `/etc/claude-code/managed-settings.json`, and blocks by exiting 2 with the remedy on stderr: the container runs with `--dangerously-skip-permissions`, so anything the permission mode can switch off is not a mechanism here. `/etc/claude-code/CLAUDE.md` carries the matching instruction — announce these commands, do not attempt them. Both live on the read-only rootfs outside the bind-mounted workspace, so they apply to whichever project is mounted and cannot be disabled from inside it. Widening the sandbox is still `allowed-domains.txt`; this is the opposite direction, and it is deliberately bypassable (`HOST_ONLY_GUARD_BYPASS=1`) because it is not a containment control. The list now spans two enforcement mechanisms, and the entry comments say which is which: the firewall plus absent credentials (wrangler, `gh`, `git push`), and the read-only `.git` mount (every other git entry). Neither of them is the guard. That is the point to hold on to when editing it — the guard cannot make a command impossible and is not trying to. Its failure mode is an agent that meets `fatal: Unable to create '.../index.lock': Permission denied` and concludes the repository is broken. Two consequences follow. The bypass is harmless on a git entry: it gets the command past the filter and into the same mount, which refuses it anyway, so the bypass costs the explanation and nothing else. And a future entry that *nothing* else enforces would be a request rather than a rule — if you add one, say so in its comment, because the file's header promises the opposite. The hook sits on the Bash **tool**, so a `git commit` inside a script the agent runs is never seen by it; the mount still is.

Seven subtleties in `verify.sh` worth knowing before editing it:

- Reachability is judged by curl's `%{time_connect}`, not its exit code. A TLS or certificate error happens *after* a successful TCP connect, so exit-code-only logic would score a reachable host as blocked. Preserve this distinction in any new probe.
- Reading iptables needs root, so the script re-execs `/usr/local/bin/verify.sh --iptables-only` under a narrow passwordless sudo entry and folds the child's counts back via the `__VERIFY_COUNTS__`/`__VERIFY_FAILED__` trailer. That sudo entry (in the Dockerfile) names the installed path, so editing the working-tree copy alone leaves a stale installed copy — the script detects a missing trailer and fails loudly rather than silently skipping the check.

- The entrypoint-marker check (`/tmp/.sandbox-firewall-installed`) is a configuration check, not an attestation. `/tmp` is a tmpfs recreated on every start, so the marker's presence means the entrypoint ran *this* start — which is the property a bare `docker start` used to violate. The agent can write `/tmp` and could forge it; that is accepted, because the containment boundary is netfilter and the read-only rootfs, not this file.

- The PID 1 line next to it reports *context*, never attribution, and the distinction is not pedantry. `entrypoint.sh` ends in `exec "$@"`, which replaces its own process, so PID 1 is the container's command whether or not the entrypoint ran — the two cases are byte-identical in `/proc/1/cmdline`. Only the marker detects a bypass. What PID 1 *does* identify is *which* command is running, and that names the cause: the CLI's shim and the image's keep-alive are both `sleep 1 & wait` loops, but only the CLI's carries an `exec "$@"`, so finding that as PID 1 means `overrideCommand` is back on. `PID1_KEEPALIVE` in `verify.sh` is the one thing it knows about the Dockerfile's `CMD`; change the `CMD` text without it and every launch reports a false FAIL.

- The host-only-command probes exercise the guard rather than reading its configuration, and check both directions: a declared command must be blocked and an ordinary one must not. Over-blocking is as much a failure as under-blocking, since it would leave the agent unable to work. They also assert the guard fails *closed* on a missing list. `HOST_ONLY_SAMPLES` and `HOST_ONLY_ALLOWED` are the only things `verify.sh` knows about the list's contents. The first carries one command per declared family — wrangler, git, `gh` — so dropping a whole family fails the launch rather than passing unnoticed; if a family is ever dropped on purpose, drop its sample too. The second is the over-blocking side, and `git tag -l` is its sharp edge: the list declares `tag`'s mutating forms only, so a pattern tightened by mistake would take a read command away in silence.

- The read-only-repository check (10) probes the *resolved* git directory from `git rev-parse --absolute-git-dir`, not the literal `.git` path, because in a worktree or submodule `.git` is a file pointing elsewhere and mounting that file read-only leaves the real git directory writable. It probes by creating a file rather than `touch`-ing one — `touch` on an existing path only updates mtime, which can succeed where a create would fail. It checks both directions, since a repository the agent cannot *read* is as broken as one it can write. And it resolves the workspace with no cwd fallback: `git rev-parse` from wherever the script is standing can find a different repository, which would turn “this workspace is not a repo” into a silent probe of some other one. A workspace with no repository reports N/A — deliberately neither a pass nor a FAIL, because a silent pass is indistinguishable from a protection that stopped working.

- A writable directory is not necessarily a usable one. The npm-cache check probes writability and executability *separately*, because a cache on a `noexec` mount clears the `EROFS` and then fails one step later at exec time with 126 — a writability-only check would score that broken state as healthy. Any future check of a writable mount that tools execute from needs the same pair of probes. The cache path comes from `npm config get cache` rather than a literal, so a base image that moves npm's default is reported rather than silently reintroducing the bug.

Distinguish `bad` (FAIL, exits non-zero, blocks launch) from `warn` (WARN, informational) when adding checks: a check promoted to FAIL will prevent every container from starting.
